What could have gone wrong is using the wrong awk field for the IP or skipping the first sort so uniq only counted adjacent lines. I could also have missed rotated logs and understated the total. The first evidence I checked was journalctl -u ssh --no-pager -n 100 and ls -la /var/log/auth.log to confirm the source existed and see its size. I tried the field print loop on a few Failed password lines to map which number held the source address. That confirmed field 11 on the standard lines. Adding the missing sort before uniq -c fixed the ranking so the counts stopped coming back as 1. I verified by running both the correct pipeline and the deliberately broken one side by side and seeing the difference in the numbers. The security impact is that a wrong field or incomplete log set would either blame the wrong source or hide the real volume, so the handoff to the lead would not be defensible.
